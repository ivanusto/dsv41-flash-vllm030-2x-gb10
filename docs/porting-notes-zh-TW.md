# 當上游引擎改版，社群配方就壞了：把雙機推論配方移植到新版 vLLM 的完整紀錄

> 這是本 repo 對應的中文文章草稿，敘述這次移植的過程、判斷依據與踩到的坑。
> 程式與差異檔在 [`files/`](../files) 與 [`patches/`](../patches)，量測條件見 [`RESULTS.md`](../RESULTS.md)。

## 摘要

推論引擎每次改版，社群為特定硬體寫的配方就有一次歸零的風險。本文記錄一次完整的移植：把一份為
2026-09-11 nightly 版寫的雙機 DeepSeek V4.1 Flash 配方，搬到官方正式版 vLLM 0.30.0 上，在兩台
GB10（各 128 GB 統一記憶體）以張量平行跨機運作。

結論先講：**可以跑，但原版引擎不足以開箱即用**。七個補丁裡有兩個完全失效、一個已被官方參數取代、
一個在自動套用時安靜地落到錯誤位置；另外還有一個 GPU kernel 缺了雙機需要的實體化版本，必須自行編譯。
整個移植最後只剩九個檔案的修改，但要找出「哪九個」與「改在哪裡」，才是真正的工作。

## 一、問題的形狀

這個模型有兩個特別之處，決定了移植的難度。

第一，它有一組叫做 Engram 的查表權重，每張卡分到約 47 GiB。在一般伺服器上可以把這張表放主機記憶體，
需要時再讓 GPU 讀。但在統一記憶體架構的機器上，「主機記憶體」和「顯示記憶體」是同一池，這個做法一點好處也沒有。
社群配方的解法是讓這張表**留在磁碟**，每一步只讀當下用到的那幾列，在 CPU 上解量化後送進 GPU。
主權重約 100 GiB 加上這 47 GiB，本來就塞不下 128 GB，所以這不是優化，是能不能跑的前提。

第二，跨兩台機器做張量平行時，注意力的 kernel 是按「每張卡幾個頭」預先編譯的。兩台機器的分法和四台機器不同，
一份為四台寫的補丁直接拿來用，只會得到一樣的錯誤。

## 二、先選對檢查點

原版引擎只認得它自己支援的量化格式，社群常用的 EXL3 不在其中。加上兩台機器的容量上限，能選的其實很少：

| 候選 | 格式 | 大小 | 可否用原版引擎 |
|---|---|---|---|
| [Mia-AiLab EXL3 2.9bpw](https://huggingface.co/Mia-AiLab/DeepSeek-V4.1-Flash-EXL3-2.9bpw)、[3.0bpw](https://huggingface.co/Mia-AiLab/DeepSeek-V4.1-Flash-EXL3-3.0bpw)、[coolbho3k 3bpw](https://huggingface.co/coolbho3k/DeepSeek-V4.1-Flash-EXL3-3bpw) | EXL3 | 197 到 400 GiB | 否，需要配方自帶的載入器 |
| [nvidia NVFP4](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4) 與第三方 FP8 | 原生格式 | 475 到 491 GiB | 格式可以，但兩台放不下 |
| [LibertAI REAP-256E](https://huggingface.co/LibertAIDAI/DeepSeek-V4.1-Flash-REAP-256E)（384 個專家剪到 256） | 專家 MXFP4、其餘 FP8 | 196 GiB | **可以** |

只有最後一個同時滿足格式與容量，也就是 LibertAI 的 REAP-256E。代價是品質：作者自己載明剪枝讓文字困惑度上升約 14.1%、圖片說明上升 8.9%，而且該配方本身把上下文限制在 32K。
這兩點在動手前就要想清楚，因為它們決定了移植成功之後這個配方能不能真的拿來用。

還有一個細節容易漏掉：REAP-256E 的倉庫**沒有附 Engram 的那兩個分片**（編號 47 與 48），要從原始模型取得。
如果機器上已經跑過同一個模型的其他量化版本，那兩個分片通常就在本機，可以直接接進來，省下數十 GB 的下載。

## 三、移植的五個發現

### 1. 改名就讓整檔掛載全部失效

新版把模型程式的目錄改了名，並把 Engram 相關的程式拆成兩個檔案。原配方的做法是「準備好整個檔案，啟動時覆蓋掉映像裡的同名檔」。
目錄一改，這種掛載要嘛掛到不存在的路徑，要嘛掛上去的是舊版程式，把新版的修正一起蓋掉。

**做法**：不要沿用整檔覆蓋。找出原配方的**差異**（多數專案會附 diff），逐一評估每一段在新版還需不需要，再套到新版檔案上。

### 2. 自動套用的模糊比對會把程式碼放到錯的地方

套補丁工具在上下文對不上時，會降低比對嚴格度去「盡量套上」。其中一段就這樣被塞進了另一個函式的 return 敘述中間：

```python
            alignment=(
                576
                if uses_fp8_ds_mla_layout and not _use_v41_mxfp8_kv_record()
        if _dsv41_indexer_sm12x():            # 被塞進來的兩行
            return DeepseekV4IndexerSM12xBackend
                else 512
            ),
        )
```

這段之所以被抓到，是因為它剛好造成語法錯誤。如果落點再偏一點，變成語法合法但語意錯誤，就會一路帶到執行期，
最後表現成某個難以解釋的品質問題。

**做法**：允許模糊比對，但每一個「勉強套上」的段落都要人工看過，套完務必做一次語法檢查。順帶一提，
同一個補丁引用的類別在新版也被改了名，要改成繼承新的基底類別。

### 3. 有些補丁已經不必存在

原配方有一段是強制改用某個 top-k kernel，因為預設的那個在這張卡上會超出共用記憶體。
新版把這個選擇做成了正式參數，一個啟動旗標就能指定。

**做法**：移植前先查上游有沒有把同樣的修正收進去，或做成可設定項。收進去的就刪掉，做成參數的就改用參數。
每刪掉一個補丁，之後每次改版就少一份維護成本。

### 4. 上游還沒合併的修正，可以只取需要的部分

[vLLM #57028](https://github.com/vllm-project/vllm/pull/57028)（zhao6300 提出，撰稿時仍未合併）處理的正是這張卡的分頁幾何問題。它的修改和原配方有一段重疊，
但另外還帶了兩個空批次的保護。我的做法是：重疊的部分沿用原配方（因為那份已經在實機跑過），
另外兩個保護從上游 PR 取用。

**做法**：把「已經被實機驗證過」和「上游認為正確」當成兩個不同的來源，逐段挑選，而不是二選一。

### 5. kernel 的實體化和平行度綁在一起

注意力 kernel 依「每張卡的頭數」預先產生。兩台機器分到的頭數是四台的兩倍，
而函式庫沒有內建這個尺寸。原配方附了修改原始碼的補丁，但映像裡有預先編譯好的產物，
會讓即時編譯整個跳過，補丁形同不存在。

**做法**：把預編目錄用空目錄遮蔽，逼它走即時編譯，編完後用符號表確認目標 kernel 真的存在。
不要看到「建置成功」就當作完成，因為建置本來就會成功，只是產物是舊的。

## 四、Engram 讀磁碟：怎麼確認自己沒寫錯

這是移植裡唯一需要重寫的部分。原本的實作和舊版程式糾纏在一起，新版的結構反而更清楚：
查表的類別已經把「怎麼配置權重」與「怎麼取用權重」拆成可以覆寫的方法，所以磁碟模式可以做成一個選項，
不去動共用的程式路徑。

真正的問題是：怎麼知道自己在 CPU 上重寫的解量化，和 GPU 上那支 kernel 算出來的完全一樣？

我的做法是寫一支對照測試，用真的安全張量檔當輸入，同時跑兩條路徑，比較輸出：

- 兩種分片切法，確認每張卡只讀自己那段列，而且起始位移正確。
- 補位的頭與「不屬於這張卡」的列，兩條路徑都要寫出零。
- 重複的 id 與無效 id，確認去重之後還能還原回原本的順序。

驗收標準訂在**逐位元相同**，不是誤差夠小。這類查表沒有浮點累加順序的問題，本來就該完全一致；
如果只要求「接近」，就會把真正的缺陷放過去。實測兩個切片都逐位元相同，這條路徑才算可信。

值得一提的是，這個模式必須關掉 CUDA graph，因為每一步都要回到主機讀檔。程式裡直接在圖擷取時丟出明確的錯誤，
而不是讓它默默產生錯誤結果。

## 五、結果

移植後的組態：官方正式版映像，加上九個檔案的修改與一個自行編譯的 kernel，兩台機器張量平行，
以 RoCE 直連，32K 上下文，關閉 CUDA graph，開啟投機解碼。

**啟動**：主權重 48 個分片從網路檔案系統載入 22.6 分鐘，投機解碼的草稿模型再掃一輪約 44 分鐘，
加上剖析與暖機，合計約 69 分鐘可服務。KV 池 372,529 個 token。

**功能全部通過**：

- 對數機率是有限值（這項是用來抓 NaN 的，輸出變成 NaN 時內容看起來仍然正常，只有這裡會顯示出來）
- 兩萬六千 token 的針取回正確
- 工具呼叫與結果回填正確
- 繁體中文短文與一萬一千 token 長文，簡體字零個，語意正確
- 思考模式開啟時推理正常、答案正確

**效能**：單路解碼每秒 9 到 10 個 token，八路併發總吞吐每秒 31.5 個，暖啟動首個 token 延遲 0.92 秒。
解碼期間 GPU 使用率 83% 到 96%，屬於計算受限。這個數字只有配方作者公布值的一半左右，原因沒有再追。

**誠實的結論**：移植成功，但這個組合不會取代現有的服務。32K 上下文擋住長對話，剪枝有品質代價，
速度也比現行配方慢。實驗的價值在於確認一件事：**上游雖然正式支援了這個模型，但在這張卡上還沒有到開箱即用**，
缺的是雙機的 kernel 實體化與分頁幾何的修正，而後者的上游 PR 還沒合併。

## 六、方法學

數字若不附條件就沒有意義，這節把這次量測的條件寫清楚，方便判讀與重現。

**軟硬體**

| 項目 | 值 |
|---|---|
| 機器 | 兩台 GB10，各 128 GB 統一記憶體，以 200 Gb 等級網路直連，NCCL 走 RoCE v2 |
| 引擎 | 官方映像 vLLM 0.30.0（aarch64），torch 2.13.0+cu130，FlashInfer 0.6.18.post1 |
| 驅動 | 580.178.04。**與配方作者的基準（580.173.02）不同**，所以跨配方比較時這是一個未受控的變因 |
| 權重 | REAP-256E，固定於撰稿時的最新修訂版；Engram 分片取自原始模型 |
| 啟動參數 | 張量平行 2、32K 上下文、最大併發序列 8、單批 4096 token、GPU 記憶體比例 0.90、關閉 CUDA graph、投機解碼 k=5、純文字模式、思考預設關閉 |

**測試腳本的來源**

- 正確性用的是配方作者附的驗證腳本，未修改。它刻意用預設請求形狀（不帶任何選用旗標）測一次，
  因為只在自訂形狀下測會漏掉預設行為的問題。
- 效能與品質用的是我自己既有的一組腳本，和先前量測同一台機器上其他配方時用的是同一份，
  所以本文的對照數字（例如 EXL3 路線的每秒 26 到 37 個 token）是同工具、同提示、同取樣條件下得到的。

**量測條件**

- 解碼速度：400 token 的繁體中文散文生成，溫度 0，串流計時，併發 1、2、4、8 各兩輪，
  取每一路的解碼速率與總吞吐。單路數字另外再單獨重測三輪，因為併發測試會在同一個伺服器上留下排隊效應。
- 首個 token 延遲：同一段 7,813 token 的提示連送三次，第一次為冷、後兩次為暖。
  這台的前綴快取會命中，所以**暖啟動的數字不能拿來當冷啟動用**，兩者要分開報。
- 針取回：在 13,835 與 26,030 token 的長文中埋入隨機代碼，要求原樣取回，溫度 0。
- 中文品質：短文與 11,126 token 長文，溫度 0 與 1.0 各一次，機械統計輸出中的簡體字數量，
  再人工讀過語意。這裡不用「和參考答案逐字相同」當標準，因為長提示下分歧本來就是預期行為。
- 系統面：解碼期間同時取樣 GPU 使用率與虛擬記憶體統計，用來分辨「計算受限」與「被磁碟或置換拖住」。
  這次確認是前者：GPU 使用率 83% 到 96%，置換換入接近零。

**這次量到的限制，以及沒有做的事**

- 單路解碼在不同輪次落在每秒 7.4 到 15.8 個 token，區間不算窄。文中引用的 9 到 10 是重測後的中位水準，
  但樣本數少，應該當作數量級而不是精確值。
- 只跑了一組啟動參數。記憶體比例與 KV 大小都沒有調校過，而就緒後可用記憶體僅剩約 2 GiB，
  這很可能就是速度只有作者公布值一半的原因之一，但**沒有驗證**，所以文中不把它寫成結論。
- 沒有自行量測困惑度，品質數字引用自模型作者。
- 每項測試各跑一次或兩次，沒有做統計顯著性。
- 這是實驗環境，不是正式服務，量測期間機器上沒有其他工作負載。

## 七、可以帶走的方法

1. **先確認格式與容量**，再談移植。格式不被原版引擎支援的檢查點，補丁再多也沒用。
2. **用差異，不要用整檔**。整檔覆蓋在改版時會把上游修正一起蓋掉，而且失效時未必看得出來。
3. **每一段勉強套上的補丁都要人工複查**，並在套完立刻做語法檢查。
4. **移植前先查上游收了什麼**。已收進去的刪掉，做成參數的改用參數。
5. **重寫的計算要有逐位元的對照測試**，而且測試要涵蓋邊界：分片切法、補位、無效值、重複值。
6. **建置成功不等於補丁生效**。預編產物會讓原始碼層級的修改完全失效，要用符號表之類的方式確認。
7. **先寫下這次移植成功之後要拿它做什麼**。這次的答案是「不取代現有服務」，而這個答案在動手前就能推得出來，
   寫下來可以避免最後被沉沒成本推著走。
